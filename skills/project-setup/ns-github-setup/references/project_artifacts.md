# SDF / GitHub Project Artifacts — Shared Contract

`ns-github-setup` provisions a small set of project-level files that the **rest of the framework depends on**. Any skill that creates, configures, deploys, tests, or hands off a NetSuite object has to respect them, or the team's CI/CD and drift detection silently break. This document is the single source of truth for what each artifact is, where it lives, who writes it, and which skills read it.

> If a project has **not** run `ns-github-setup`, none of these files exist yet. In that case a skill should note the gap and either proceed in standalone mode or point the user to `ns-github-setup` — but never invent a conflicting structure.

---

## The Artifacts

| Artifact | Location | Tracked in Git? | Purpose |
|---|---|---|---|
| `OBJECT_OWNERSHIP.md` | project root | ✅ committed | Registry of SDF-owned vs UI-owned vs Shared objects. The human-readable source of truth for "who may change this object and how." |
| `ci/objects-manifest.json` | `ci/` | ✅ committed | Machine-readable list of **SDF-owned** objects, consumed by `ci/check-drift.js`. Mirrors the SDF-Owned section of `OBJECT_OWNERSHIP.md`. |
| `ci/generate-deploy.js` | `ci/` | ✅ committed | Generates `deploy.xml` at CI time from the git diff (Strategy B). Replaces manual `deploy.xml` editing. |
| `ci/check-drift.js` | `ci/` | ✅ committed | Pre-deploy drift detection — imports SDF-owned objects from the account and fails the pipeline if the account drifted from Git. |
| `.github/workflows/sdf-deploy.yml` | `.github/workflows/` | ✅ committed | The GitHub Actions CI/CD pipeline: `validate` → `deploy-sandbox`/`deploy-production` → `drift-check`. The automated gate for every PR. |
| `ci/setup-complete.json` | `ci/` | ✅ committed | Record that `ns-github-setup` has run. Carries `deployStrategy`, `branchModel`, `environments`, `driftDetection`. Detecting it tells a skill the pipeline already exists. |
| `deploy.xml` | project root | ❌ **gitignored** (Strategy B/C) | Generated per-environment by `generate-deploy.js`. **Never** hand-edit a committed `deploy.xml` — under Strategy B it is gitignored and editing it does nothing in CI. |

---

## The Three Golden Rules

1. **New SDF object → three files move together.** Whenever a new SDF-owned object is created (`customscript_*`, `scriptdeployment_*`, a custom field/record, a custom segment, etc.), it must be added to **(a)** the `Objects/` folder XML, **(b)** `OBJECT_OWNERSHIP.md` (SDF-Owned section), and **(c)** `ci/objects-manifest.json`. Miss (b) and ownership is ambiguous; miss (c) and drift detection silently never covers it.

2. **Decide ownership at creation, never later.** Every new object is either SDF-owned (changed via Git PR only), UI-owned (managed in the NetSuite UI, excluded from `deploy.xml`/`Objects/`), or Shared (SDF tracks for documentation, UI is authoritative). Use the **Ownership Decision Guide** in `assets/OBJECT_OWNERSHIP.md`. Default to SDF-owned when unsure and mark it "pending confirmation."

3. **Never instruct manual `deploy.xml` editing under Strategy B/C.** `deploy.xml` is gitignored and regenerated by CI. Deployment is selective and automatic via the git diff. Skills that used to say "edit deploy.xml" must instead reference `ci/generate-deploy.js` and the GitHub Actions pipeline. (Strategy A — wildcard deploy-all — is the only case where a committed `deploy.xml` is expected; check `ci/setup-complete.json` → `deployStrategy`.)

## Default Ownership at a Glance

| Object Type | Default | Notes |
|---|---|---|
| SuiteScript (any type) | **SDF** | Always. Never UI-owned. |
| Script Deployment | **SDF** | Always. |
| Custom Record / Field / Segment | **SDF** | Confirm; override to UI only for complex UI-managed form logic. |
| Custom List | **SDF** | UI-owned if values change frequently via the UI. |
| Saved Search | **UI** | SDF only if fully generic with no account-specific values. |
| Custom Form | **UI** | Per-environment form assignments. |
| SuiteFlow Workflow | **UI** | Complex state managed by functional team; SDF only if fully generic (rare). |
| Custom Role | **UI** | Permissions vary per environment. |

Full guide and override conditions: `assets/OBJECT_OWNERSHIP.md` (Ownership Decision Guide section).

## Which Skill Touches Which Artifact

| Skill | Interaction |
|---|---|
| `ns-github-setup` | **Creates** all artifacts (one-time setup). |
| `ns-solution-architect` | **Declares** intended ownership per object in each Customization Spec, so downstream skills populate the registry correctly. |
| `ns-configurator` | **Writes** ownership decisions for fields/records/lists/forms/searches to `OBJECT_OWNERSHIP.md`; adds SDF-owned ones to `ci/objects-manifest.json`. |
| `ns-suitescript-dev` | **Registers** new `customscript_*` / `scriptdeployment_*` (always SDF-owned) in both `OBJECT_OWNERSHIP.md` and `ci/objects-manifest.json`; uses `generate-deploy.js` + Actions for deployment. |
| `ns-workflow-dev` | **Documents** workflows (usually UI-owned) in the UI-Owned section; if SDF-managed, adds to the manifest. |
| `ns-object-sync` | **Reads** `OBJECT_OWNERSHIP.md` to gate sync; **appends** to `ci/objects-manifest.json` if missing. |
| `ns-pr-create` | **Verifies** new `Objects/` XML is paired with `OBJECT_OWNERSHIP.md` + `ci/objects-manifest.json` updates. |
| `ns-pr-merge` / `ns-ci-diagnose` / `ns-conflict-resolve` | **Read** `ci/setup-complete.json`, the workflow, and `deploy.xml` strategy to drive merge/diagnosis/conflict rules. |
| `ns-init-workspace` | **Detects** `ci/setup-complete.json`; optionally **seeds** an empty `OBJECT_OWNERSHIP.md` and a TODO item. |
| `ns-erp-navigator` | **Flags** `ns-github-setup` as a Phase 3 (Build) prerequisite and gate check. |
| `ns-test-manager` | **Treats** the Actions pipeline (`validate` + unit tests + drift-check) as the automated SIT gate; confirms drift passes before UAT. |
| `ns-data-migrator` | **Confirms** it does not create SDF-tracked objects without an ownership declaration. |
| `ns-change-orchestrator` | **Trains** the client's internal team on the GitHub branching/PR/deploy workflow for post-go-live maintenance. |
